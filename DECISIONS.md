# DECISIONS.md

## Decision 1: Start Documentation First

Decision:
Start with documentation before building apps.

Reason:
Codex needs clear context to understand the Helios Agent System.

## Decision 2: Core Boys International Is the First Build

Decision:
Build the Core Boys International tracker before Midas, Vitalis, or the full Life OS.

Reason:
Core Boys has the clearest path toward content planning, analytics, automation, and monetization.

## Decision 3: Use Simple Storage First

Decision:
Use local JSON, in-memory data, or simple files for the first MVP.

Reason:
A real database is unnecessary before the tracker workflow is proven.

## Decision 4: Keep Notion and Codex Separate at First

Decision:
Use Notion for organization and Codex for building tools.

Reason:
Notion is better for flexible planning. Codex is better for structured tools and automation.

## Decision 5: Do Not Build the Full Life OS First

Decision:
Delay the full Helios Life OS command center until smaller tools prove useful.

Reason:
Building the full system too early creates complexity before workflows are clear.

## Decision 6: Keep Agent Roles Stable

Decision:
Do not rename or redesign the agents without explicit user approval.

Reason:
The agent system already has meaning and structure. Codex should preserve it.

## Decision: Forge and Achilles Are Separate

Decision:
Forge is the technical builder for code, tools, apps, scripts, and prototypes.
Achilles is the Notion and system architect for pages, databases, dashboards, templates, and workflows.

Reason:
Separating them prevents Codex from treating every system-building task as a coding task.

## Decision: Core Boys Is First, Not Everything

Decision:
Core Boys International is the first build target because it has a clear MVP.
It should not make the whole repo only about content.

Reason:
The Helios system is broader than one project.

## Decision: Helios Routes First

Decision:
Broad or unclear requests should go through Helios first before selecting an agent.

Reason:
Helios keeps the full system organized and prevents random building.

## Decision: Claude Is Advisory-Only in Phase 1

Decision:
Claude is added as an external advisory lane for second-opinion writing, review, and synthesis.
Claude is not the default execution owner for implementation, integration, or validation in phase 1.
Helios remains final router and decision owner.

Reason:
This keeps quality benefits from second-opinion passes while preserving clean ownership, reducing routing confusion, and preventing parallel-system drift.

## Decision: Unified App Name Is Knova

Decision:
Use `Knova` as the long-term unified app name for the Helios system.

Reason:
`Knova` is more distinctive than `Nova`, reduces naming ambiguity, and preserves naming continuity across current planning docs.
