# Knova Read-Layer v1 Spec

## Status

Planning only.

No code changes in this spec.

## Purpose

Define a read-only Knova prototype that unifies current module visibility from:

- `apps/core-boys-tracker`
- `apps/intake-router`

Knova v1 read layer should provide one-screen weekly clarity without modifying module internals.

## Scope

Included:

- Read contracts for module exports
- One-screen layout sections
- Aggregation logic rules
- Acceptance checklist

Excluded:

- Write actions
- Module-side refactors
- Backend/database/auth
- Notion sync automation

## Canonical Inputs

Current module storage keys:

- Core Boys entries: `core_boys_tracker_v1`
- Core Boys CapCut templates: `core_boys_capcut_templates_v1`
- Intake Router submissions: `helios_intake_v1`

Read-layer must tolerate missing keys and malformed records gracefully.

## Read Contract Standard (Required)

Each module provides three artifacts:

1. `status.json`
2. `weekly-summary.md`
3. `issues.md`

For v1 prototype, these can be generated by Knova on read (derived contract) before module-native export scripts exist.

## Contract: Core Boys Tracker

## `status.json`

```json
{
  "module": "core-boys-tracker",
  "lastUpdated": "ISO-8601",
  "activeItemsCount": 0,
  "blockedItemsCount": 0,
  "signals": {
    "totalEntries": 0,
    "readyToPost": 0,
    "postedEntries": 0,
    "totalViews": 0
  }
}
```

Derivation notes:

- `totalEntries`: entry count
- `readyToPost`: status = `Ready`
- `postedEntries`: status = `Posted`
- `totalViews`: sum of `views` (numeric coercion, fallback 0)
- `activeItemsCount`: statuses in `Idea|Editing|Ready`
- `blockedItemsCount`: entries flagged by missing required fields for execution context (e.g. missing hook/platform/status) or explicit local blocker tag if later added

## `weekly-summary.md`

Required fields:

- Signal
- Decision
- Next Action
- Owner

Core Boys v1 owner default:
- `Forge` for tracker execution context
- `Kirin` for creative angle notes when present
- `Helios` for final weekly routing note

## `issues.md`

Minimum:

- Known blockers list
- Data quality risks list
- Manual workaround notes

## Contract: Intake Router

## `status.json`

```json
{
  "module": "intake-router",
  "lastUpdated": "ISO-8601",
  "activeItemsCount": 0,
  "blockedItemsCount": 0,
  "signals": {
    "totalSubmissions": 0,
    "newSystemBlocked": 0,
    "unclearRoutedToHelios": 0,
    "forgeCodexRouted": 0
  }
}
```

Derivation notes:

- `totalSubmissions`: entries count
- `newSystemBlocked`: `scopeBoundary = new-system` (or `unclear` if policy blocks submit path)
- `unclearRoutedToHelios`: `domain = unclear` or `requestType = unclear` routes
- `forgeCodexRouted`: `routedTo = Forge -> Codex`
- `activeItemsCount`: submissions in current review window
- `blockedItemsCount`: submission attempts rejected by validation are not stored now; v1 uses `newSystemBlocked` as proxy blocker count

## `weekly-summary.md`

Required fields:

- Signal
- Decision
- Next Action
- Owner

Intake Router v1 owner default:
- `Helios` (routing gate)
- `Strategos` for scope/risk trend note when needed

## Aggregation and Parsing Rules

1. Parse defensive:
- malformed JSON -> section warning, not app crash

2. Time windows:
- default 7-day rolling window, configurable

3. Numeric coercion:
- non-numeric KPI values -> treat as 0, log warning

4. Missing contract artifact:
- show module as `Contract Missing` with guidance

5. Ordering:
- sort modules by blocker count descending in risk section

## Empty States

Required:

- No module data: `No module exports found yet.`
- Contract missing: `Contract missing for [module].`
- No weekly summary: `No weekly summary yet for this module.`

## Read-Layer Acceptance Checklist

Prototype is complete only when all are true:

1. One screen shows weekly priorities + module snapshots + issues + decision preview.
2. Core Boys metrics render from local data without manual hand-edit.
3. Intake Router routing metrics render from local data without manual hand-edit.
4. Missing/malformed data never crashes the read layer.
5. Every section supports empty state text.
6. No write operations are performed on module internals.
7. Output is readable in under 2 minutes.
8. Mobile width 375px has no horizontal overflow.

## Risks and Guardrails

Risks:

- Contract drift between modules
- Implicit schema assumptions
- Overfitting read layer to temporary fields

Guardrails:

- Keep contracts minimal and explicit
- Version contracts when changing fields
- Keep module internals decoupled from Knova UI logic

## Open Decisions Before Build

1. Should `blockedItemsCount` in Core Boys be strict schema-based only, or include heuristic execution blockers?
2. Should Knova persist read-layer snapshots, or remain purely live-derived in v1?
3. Should weekly summaries be generated in-module or by Knova aggregator for v1?

Default for v1:
- heuristic blockers allowed
- no persistence
- Knova aggregator generates summaries if missing

- Core Boys snapshot default owner: Kirin for content direction; Forge/Codex only for technical tracker output
- Intake Router snapshot default owner: Helios
- Weekly priorities default owner: Strategos
- Risk/issues section default owner: Helios

When source artifacts include explicit owners, source owners take precedence over defaults.
