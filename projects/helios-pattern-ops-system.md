# Helios Pattern Ops System

## Purpose

The Helios Pattern Ops System turns repeatable real-world patterns into real opportunities, then moves them through clear planning and execution.

This system is based on one core principle:

Pattern recognition compounds results when the pattern is captured early, scored clearly, executed with discipline, and reviewed for reuse.

## Why This Is a Core Helios Project

- It supports all domains, not only content.
- It gives Helios a repeatable way to convert signals into action.
- It keeps execution practical and prevents random idea chasing.
- It creates reusable playbooks instead of one-off wins.

## Pattern Types to Track

- Seasonal demand patterns (summer, winter, holidays)
- Major game/event release windows
- Sports cycles (World Cup, playoffs, transfer windows)
- Market structure events (IPO calendars, index adds/drops)
- Economic policy windows (Fed announcements, macro reports)
- Creator/internet trend cycles
- Group/community formation moments
- Platform feature or algorithm shifts

4. Execution playbook standard

## Agent Ownership Model

- Helios: Router, final decision gate, weekly direction
- Atlas: Pattern research, source evidence, timing windows
- Strategos: Prioritization, sequencing, tradeoff decisions
- Midas: Money potential, risk, downside controls
- Vitalis: Human sustainability and routine feasibility checks
- Kirin: Creative angles, hooks, narratives, campaigns
- Achilles: Notion system architecture and documentation structure
- Forge: Tooling, trackers, local execution systems, automation later

## Progressive Pipeline Stages

1. Capture
2. Validate
3. Score
4. Plan
5. Execute
6. Review
7. Playbooked
8. Archived

## Minimum Data Model

Each pattern opportunity should include:

- Pattern Name
- Pattern Type
- Trigger Window
- Lead Time Needed
- Why Now
- Evidence Sources
- Target Outcome
- Estimated Effort
- Estimated Upside
- Downside Risk
- Kill Switch Condition
- Owner Agent
- Current Stage
- Next Action
- Review Date

## Scoring Standard (v1)

Score every opportunity on a 1 to 5 scale:

- Timing Fit
- Leverage
- Money Potential
- Ease of Execution
- Strategic Fit
- Risk Exposure (inverse score)

Use a weighted composite score for ranking, then choose top one to three opportunities only.

## Trigger Calendar Rule

Every opportunity must have:

- Trigger date or trigger range
- Preparation start date
- Decision checkpoint date
- Execution window
- Review date

If a trigger date is unknown or weakly supported, do not move beyond Validate stage.

## Experimentation Reliability Layer (v1)

When an opportunity uses A/B testing, require:

- One primary metric (decision metric)
- Two to four guardrail metrics
- Expected traffic split and randomization unit
- Minimum run window before decision
- SRM check before reading lift
- Predefined win/loss/hold thresholds

If SRM fails or guardrails break materially, mark the test invalid and do not ship.

## Primary and Guardrail Metrics Standard

- Primary metric should map directly to target outcome.
- Guardrails should protect quality, user harm, and business downside.
- Avoid changing primary metric after launch.
- Track practical impact, not significance alone.

## Peeking and Decision Rule

- Use fixed decision checkpoints or a sequential method.
- Do not make ad hoc stop decisions from random peeks.
- Every test must define stop, continue, and rollback conditions in advance.

## Variance Reduction Rule

- CUPED-style adjustment is allowed only when pre-period data quality is stable.
- If pre-period match coverage is weak, run unadjusted baseline analysis alongside adjusted analysis.
- Never use variance reduction methods to hide weak instrumentation or poor randomization.

## Execution Rule

No opportunity enters Execute stage without:

- Named owner
- Defined output
- Defined success criteria
- Defined risk and kill switch
- Defined review date

## Weekly Decision Rhythm

1. Atlas updates evidence and timing.
2. Strategos ranks and narrows.
3. Midas checks risk and downside.
4. Kirin proposes execution angles.
5. Helios selects top opportunities.
6. Achilles keeps structure clean.
7. Forge executes selected build/tool steps.
8. Helios closes with keep/improve/stop decision.

## v1 Outputs

- Pattern opportunity log
- Weekly top opportunities list
- Trigger calendar
- One execution playbook per active opportunity
- Weekly review with keep/improve/stop decision
- Experiment reliability log (valid or invalid test outcomes)

## Do Not Build Yet

- Full predictive analytics engine
- Auto-trading logic
- Real-time market data integration
- Paid data feeds
- Complex agent backend
- Full centralized app shell

## Success Definition

The system is successful when:

- Opportunities are selected by score, not impulse.
- Execution starts earlier relative to trigger windows.
- Weekly decisions are clearer and faster.
- Repeated wins are converted into reusable playbooks.
- Weak ideas are stopped earlier with less wasted effort.
- Experiment decisions are trustworthy and reproducible.

## Recommended Build Order

1. Notion-first structure via Achilles
2. Weekly operating rhythm via Helios + Strategos
3. Local tracker support via Forge (simple first)
4. Automation only after workflow stability is proven
